# Audit complet avant le design — octobre 2026

> Consigne 23, branche `chore/audit-complet`, 2026-10-11. L'audit **ne corrige rien** dans le
> code applicatif : il ajoute des tests et ce rapport. Tout ce qui touche le projet Supabase
> distant ou le site en ligne a été fait **en lecture seule**. Aucun secret ni aucune donnée
> personnelle ici : comptes et contacts fictifs (`@example.test`), clés jamais affichées.

## 1. Résumé

1. **Base de données solide** : 598 tests pgTAP verts (84 nouveaux). Droits réels identiques à la
   matrice attendue, RLS partout, toute RPC admin refuse anon et non-admin, règles de réservation
   et d'annulation tenues aux limites, y compris sous concurrence réelle (dblink).
2. **Aucune faille de sécurité sérieuse nouvelle** : rien n'a justifié d'arrêter l'audit. Le
   schéma de production est **identique** au local, sauf un objet de la plateforme Supabase
   (A-07, clos : trigger d'événement, non appelable via l'API).
3. Les **3 bloquants** restent ouverts : CSP en `Report-Only`, anti-abus global des
   réservations, purge RGPD. La recopie de `error.message` (C-01) était le 5e : **déclassée
   en 🟡 par Thibault** (jamais affichée, 243 cas), à corriger dans la première consigne de
   correction (§6, n° 2). La règle de révélation de l'adresse (K-04) était le 4e : **résolue par
   décision le 2026-10-12** (source : Alix, consigne 24, ADR 0008) : aucune adresse stockée.
4. **Site en ligne** : en-têtes conformes à `public/_headers`, aucun fichier sensible servi,
   aucune source map, aucune clé autre que la clé publique ; CSP : **0 violation** sur 7 pages.
5. **Connexion admin** : messages indiscernables (compte inexistant / mauvais mot de passe),
   mais **aucun frein au brute-force** observé (sonde LOCALE : 40 essais en rafale, puis le bon passe ; limites de la prod non mesurées) (B-01).
6. **Robustesse** : 9 écrans × 9 pannes simulées, aucun texte technique affiché ; 4 défauts
   d'enchaînement côté client, dont le **lien d'annulation perdu** au rechargement (C-03) et
   une **réservation créée mais réponse perdue** (C-05).
7. `booking/data.ts:141` et `:161` gardent `error.message` dans l'`Error`, mais **il n'est
   jamais affiché** (vérifié sur 243 cas) : risque réel faible (C-01).
8. **Dépendances** : `npm audit` 0 faille (prod et dev) ; licences compatibles ; gitleaks :
   12 alertes, toutes le même uuid fictif de tests (aucune vraie clé).
9. **Performance mobile** : Lighthouse 80 (accueil) et 72 (réserver) ; un seul JS de 670 kB
   (193 kB gzip) qui embarque tout l'admin. Accessibilité : axe **0 violation**, Lighthouse 100.
10. **Config locale** : `[auth.email] enable_signup = false` **coupe toute connexion par
    e-mail** en local, pas seulement l'inscription (B-03).

## 3. Stabilité des tests e2e (3 passes complètes)

Suite complète (3 projets : Android, iPhone, desktop), sans reprise automatique (`retries: 0` en
local), journaux relus en entier.

| Passe | Résultat                                  | Durée   |
| ----- | ----------------------------------------- | ------- |

| 2     | 504 réussis, 24 sautés                    | 5,3 min |

- **Instabilité trouvée : mes propres nouveaux tests** « panne `timeout` » (passe 3 : réserver /
  créneaux sur iPhone, annulation / envoi sur Android). La fausse API ne répond qu'après 15 s et
  le test attendait 25 s : sous la charge de la suite complète (6 navigateurs, un seul serveur
  Vite), la marge ne suffisait pas toujours. Corrigé dans le test (attente 50 s, délai du test

- **Chaîne rejouée depuis une base vide** (`supabase db reset --local`) : les 13 migrations

  - local `393fd992bd68441cab08385f212539d5` (227 lignes), prod `7899c34f4fd1efe9ce7e64cf3c40c8c7`
    (229 lignes) ; chaque md5 recalculé sur sa copie correspond au md5 déclaré : copie fidèle ;
  - **aucune ligne locale absente de la prod** : mêmes 13 migrations, tables, colonnes,
    contraintes, triggers, politiques RLS, droits, bucket, extensions et corps des 40 fonctions ;
  - **2 lignes en plus en prod**, un seul objet : `public.rls_auto_enable()` (constat A-07, clos :
    trigger d'événement `ensure_rls` de la plateforme Supabase).

Pourquoi pas `supabase db diff --linked` : la CLI récente crée un **rôle temporaire** de
connexion sur le projet distant quand on ne lui donne pas le mot de passe : c'est une écriture.
Pourquoi pas le MCP Supabase : accès refusé (décision du 2026-10-11, le MCP sera retiré avant la
mise en ligne).

Méthode retenue : `docs/audit/empreinte-schema.sql`, **un seul `SELECT`** (aucune écriture),
qui renvoie **une seule cellule** : tables (RLS), colonnes (type, NOT NULL, défaut), contraintes,
triggers, politiques RLS (md5 des conditions), droits de `anon`, `authenticated`,
`service_role` et `PUBLIC` sur tables, colonnes, fonctions et schémas, fonctions de `public`
et `private` (`security definer`, `search_path`, md5 de `pg_get_functiondef`), bucket,
extensions et numéros de migration. Aucune ligne de table : ni donnée personnelle, ni secret.

1. Thibault lance le fichier dans le SQL Editor de la prod et copie la cellule.
2. Même fichier en local :
   `docker exec -i supabase_db_site-barber psql -U postgres -At < docs/audit/empreinte-schema.sql`.
3. Même md5 total : schémas identiques. Sinon, `diff` ligne à ligne. Écarts attendus : les
   migrations « appliquées en local seulement » (PLAN) et, éventuellement, les versions
   d'extensions (lignes `extension`) si la version de PostgreSQL diffère.
